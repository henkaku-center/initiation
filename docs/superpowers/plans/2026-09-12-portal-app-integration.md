## 質問の対応と承認された境界

初回は既存4項目を新UIへ接続する方針を依頼者が確認した。ID・必須条件・完走判定を維持する。

| 通常アプリのID | 回答形式・条件 | デモとの差分 |
| --- | --- | --- |
| q-introduction | 空白以外の文字列、必須 | curiosityとは問いの意味が異なるため自動変換しない |
| q-how-found | 空白以外の文字列、必須 | 対応するデモ項目なし |
| quest-wallet-setup | 完了の自己申告、answer=null、必須 | ウォレット接続やtokenAddedのブラウザ値から自動完了しない |
| quest-discord-hello | 完了の自己申告、answer=null、必須 | 対応するデモ項目なし |
| members.display_name | 任意、進捗テーブル外 | デモのnameから移行しない |

デモのinterests / curiosity / experience / readiness / contributionと「まだ言葉にしない」は現行保存契約と一致しない。#46の最新議論では「答えない」を空文字ではない明示値として保存する案、Discord名、Field閲覧記録、Check-inの一言が整理されているが、現行コードには未反映。今回の4項目接続でこれらの仕様を確定しない。

## 小さな変更単位と受け入れ条件

各単位はテスト追加→意図した失敗→実装→関連テストの順に進める。

1. **入口・共通UI**: `/`を新Homeにする。`/setup`、`/initiation`、`/community`、`/passport`を通常URLとして扱い、`/checkin`・`/apply`・`/admin`を維持。旧ハッシュURLも対応先へ誘導。生成HTMLの直編集はしない。通常モードでAPI/POSTが遮断されないこと、デモでは引き続き遮断されることを検証。
2. **Setup**: 接続と認証を別表示。Polygon確認後に署名。取得中・取得失敗・署名待ち・署名拒否・認証失敗を区別し、重複操作を防ぐ。切断・アカウント切替時は旧データを隠し、セッション破棄と再取得を行う。署名途中の切替も検証。
3. **Initiation**: 既存4項目と任意の呼び名。回答の保存成功を確認してから次へ進む。失敗時は入力を保持。再読込後は保存済み回答と未完了項目を復元。完走はサーバーの4項目記録を根拠とする。
4. **申請・Passport**: server側の完走チェックと重複制約を再利用。3種類の状態を別表示。rejectedのみ再申請可能、needs_infoは実装済みの状態表示まで。一般ユーザーの審査操作を出さない。
5. **Community**: 認証済み本人のチェックインと履歴。日付をブラウザ入力で指定できず、同日の重複が増えない。通信失敗・未認証を表示。
6. **表示と公開設定**: 未接続機能・サンプル表示を整理。noindexを保持。通常buildへの切替とデモbuildへのロールバック手順を文書化する。公開環境は変更しない。

## 検証方法

- 開始時に同リポジトリの開発サーバーが3000番で稼働していたため、build・ブラウザ検証は一時コピーで行う。既存.env.localは読み込まず、実認証情報を持ち込まない。
- `package.json`・CIに合わせ、通常build → `npx tsc --noEmit`、lint、unit、必要なintegration、demo buildを実行。テスト専用のローカルサービスを使い、共有開発DBを初期化しない。
- ブラウザでURLの直接表示、再読込、戻る/進む、ライト/ダーク、モバイル/タブレット/デスクトップ、キーボードを確認。署名はテスト用の応答・一時アカウントで検証し、実ウォレットには要求しない。
- Local-verified / CI-verified / Unverifiedを分け、実行したソースと結果を最終記録へ残す。
